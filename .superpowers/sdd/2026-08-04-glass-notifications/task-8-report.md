## Self-review against the seven deliberate behaviours

1. **Glass is the RFCOMM server; phone connects.** Preserved — `acceptLoop()` calls
   `serverSocket.accept()` in a blocking loop with a plain 5s idle sleep when Bluetooth is off or
   the listen call fails; no client-side connect code was added anywhere.
2. **Any `IOException` (incl. `ProtocolException`) closes the socket and returns to `accept()`.**
   Preserved — `serve()`'s single `catch (IOException e)` around the whole read loop just logs and
   returns; `finally` in `acceptLoop()` unconditionally closes the socket and server socket. No
   resync/retry-within-stream logic was added.
3. **Connections from an unpinned device are refused before a single frame is read.** Preserved —
   `serve()` checks `pin.isAllowed(address)` and returns immediately (before touching
   `socket.getInputStream()`/`FrameCodec.read`) if refused.
4. **Unknown frame types are ignored, not errors.** Preserved — `dispatch()`'s `default` case only
   logs; no exception thrown, loop continues.
5. **Version mismatch reports "phone app out of date" and returns (not a generic stream error).**
   Preserved — `serve()` checks `frame.version != Protocol.VERSION` before calling `dispatch()`,
   shows `R.string.version_mismatch` via Toast, and `return`s out of `serve()` rather than throwing.
6. **`lastApplied` starts null per new connection.** Preserved — `serve()` sets
   `lastApplied = null;` right after the pin check succeeds, before the read loop starts, so
   `InterruptPolicy.selectInterrupt(null, firstSnapshot)` returns null on the first snapshot of any
   connection (verified against `InterruptPolicy.java`'s doc/logic: `previous == null` short-circuits
   to `return null`).
7. **Debug receiver inert unless `BuildConfig.DEBUG`.** Preserved — first line of
   `DebugInjectReceiver.onReceive` is `if (!BuildConfig.DEBUG) { return; }`. Verified this actually
   compiles and behaves correctly for both build types by running `./gradlew test`, which compiles
   and unit-tests both the `debug` and `release` variants of the `glass` module.

No behaviour was softened, renamed, or "improved." No code beyond the brief's Step 1–6 content was

## Fix report: three Important lifecycle findings from review

The Task 8 review found three Important issues, all in the lifecycle surface, all present
verbatim in the brief's own code (not introduced by transcription) but undefended by the plan.
Fixed all three.

### Finding 1 — accept thread could outlive `onDestroy()` indefinitely

`acceptLoop()` only ever held the connected `BluetoothSocket` as a local variable passed into
`serve()`. `closeServerSocket()` (called from `onDestroy()`) closes the *listening* socket, but
that socket is already closed and nulled by the time a connection is being served — so during an
active connection, `onDestroy()` had nothing to close, and the accept thread stayed blocked in
`FrameCodec.read(in)` indefinitely, even after the service was destroyed.

**Fix:** added a new field `private volatile BluetoothSocket connectedSocket;` to
`LinkServerService`. It is assigned right after `accept()` succeeds and before `serve()` is
called, so it is populated for the entire time `serve()` runs. A new `closeConnectedSocket()`
method (same shape as the existing `closeServerSocket()`: read field, null field, close outside
the null check, swallow `IOException`) is called from both `onDestroy()` and the `finally` block
of `acceptLoop()`'s per-connection try. Closing it from `onDestroy()` is what now unblocks the
pending `read()` — the accept thread's `catch (IOException e)` in `serve()` catches the resulting
`SocketException`, logs "connection ended", and returns normally, letting `acceptLoop()`'s
`while (running)` exit cleanly since `running` was already set `false`.

The old `closeQuietly(BluetoothSocket)` static helper (previously called on the local `socket` in
`acceptLoop()`'s `finally`) was removed and replaced by `closeConnectedSocket()`, since the field
now needs its own null-out-then-close discipline identical to `closeServerSocket()`'s, and keeping
both a static closer and a field closer for the same socket would have been redundant.

### Finding 2 — `serverSocket` was not `volatile`

It was written on the accept thread (`acceptLoop()`) and read/nulled from the main thread
(`onDestroy()` → `closeServerSocket()`), with no synchronization or other happens-before edge
between the two threads — unlike `overlay`, which is safely published via `Thread.start()`'s
happens-before before the accept thread ever reads it.

**Fix:** changed `private BluetoothServerSocket serverSocket;` to
`private volatile BluetoothServerSocket serverSocket;`. The new `connectedSocket` field (Finding 1)
was declared `volatile` from the start for the same reason. Chose plain `volatile` on both fields,
per the review's stated preference for the smaller change, rather than introducing a synchronized
holder — no other synchronization mechanism was layered on top of either field.

### Finding 3 — `DebugInjectReceiver` built a throwaway `InterruptOverlay` per broadcast

`LinkServerService` kept one `overlay` field and reused it, so a second interrupt replaces the
first and restarts the timer (the storm-collapsing behaviour the design requires). But
`DebugInjectReceiver.notifyUi()` constructed `new InterruptOverlay(context)` fresh on every
broadcast, so two `INTERRUPT` injections inside the same ~5s window produced two independent
overlay instances that knew nothing of each other and could stack two windows — directly
reachable via the brief's own Step 7, which fires three `fake-notify.sh` calls back to back.

**Fix:** added a process-wide singleton accessor to `GlassNotify`, following the identical
`synchronized` + `context.getApplicationContext()` pattern already used by `store(Context)` and
`peerPin(Context)`:

```java
public static synchronized InterruptOverlay overlay(Context context) {
    if (overlay == null) {
        overlay = new InterruptOverlay(context.getApplicationContext());
    }
    return overlay;
}
```

`LinkServerService.onCreate()` now does `overlay = GlassNotify.overlay(this);` instead of
constructing its own instance. `DebugInjectReceiver.notifyUi()` now does
`final InterruptOverlay overlay = GlassNotify.overlay(context);` instead of `new
InterruptOverlay(context)`. Both call sites still post to the main looper before calling
`overlay.show(...)`/`overlay.dismiss()` — `notifyUi()`'s `Handler(Looper.getMainLooper()).post(...)`
and `LinkServerService`'s existing `main.post(...)` calls were not touched, so
`InterruptOverlay.show()`/`dismiss()` are still only ever invoked on the main thread.
